# 메일 발송 Tool 후속 과제

| 항목      | 값                                                                   |
| --------- | -------------------------------------------------------------------- |
| 문서 상태 | 초안                                                                 |
| 작성일    | 2026-10-14                                                           |

## 1. 개요

메일 발송 Tool 1차 구현에서 미루고 이후에 처리할 과제를 정리한다.
1차 구현은 범용 SMTP 클라이언트이며, 메일 발송 자격(비밀번호)은 가이드 10장의 예외로 허용했다(2026-10-14 결정).
비밀번호를 다루는 방식은 "일단 만들고 나중에 처리 방법을 정한다"로 결정했으므로, 그 처리 방법을 이 문서의 과제로 남긴다.

시점이 "운영 전"인 과제는 실제 사용자 데이터나 실제 계정으로 운영하기 전에 끝내야 한다.

## 2. 과제 목록

| ID   | 과제                                            | 담당         | 시점          |
| ---- | ----------------------------------------------- | ------------ | ------------- |
| F-01 | 기록의 민감정보 마스킹                          | 플랫폼       | 운영 전       |
| F-02 | Tool 설정 항목의 모델 비노출                    | 플랫폼       | 운영 전       |
| F-03 | 설정에 저장된 민감정보 보호                     | 플랫폼       | 운영 전       |
| F-04 | 실제 메일 서비스 검증                           | Tool         | 운영 전       |
| F-05 | 수신자 통제                                     | Tool, 플랫폼 | 운영 중       |
| F-06 | OAuth2 로그인 지원                              | Tool         | M365 사용 시  |
| F-07 | 첨부 파일 지원                                  | Tool, 플랫폼 | 요구 발생 시  |
| F-08 | 중복 발송 방지                                  | 플랫폼       | 요구 발생 시  |
| F-09 | 샌드박스 밖 메일 게이트웨이                     | 플랫폼       | 1단계 운영 후 |
| F-10 | Tool 실행 격리 (Worker 보호, UID·컨테이너 분리) | 플랫폼       | 운영 전       |
| F-11 | SMTP 서버 주소를 통한 내부망 접속 방지 (SSRF) | 플랫폼, Tool | 운영 전 |

F-01~F-03은 서로 맞물린다. 비밀번호가 지나가는 경로를 모델(F-02), 저장소(F-03), 기록(F-01)으로 나눈 것이다.
F-11은 F-02와 함께 처리한다. 모델이 `smtp_host`를 정할 수 있으면 내부망 접속과 자격 탈취 경로가 함께 열린다.
샌드박스 안의 경로는 F-10(Tool 실행 격리)과 F-09(비밀번호를 샌드박스에 두지 않기)가 다룬다.
사내 무인증 릴레이(`smtp_auth=none`, 2026-10-19 추가)를 쓰면 비밀번호가 없으므로 F-01·F-03·F-09의 비밀번호 관련 범위는 해당하지 않는다.
대신 F-02(모델이 발신 주소를 바꾸는 위장)와 F-05(발송량)가 더 중요해진다.
전달 방식 조사와 근거는 `tool-설정-전달-조사.md`에 있다.

## 3. 과제 상세

### 3.1. F-01 기록의 민감정보 마스킹

**배경.** 비밀번호는 Agent 설정의 Tool 설정값으로 입력되고, Tool을 호출할 때 함수 인자로 전달된다.
이 값이 지나가는 곳 중 기록을 남기는 곳에 원문이 저장되면, 기록을 열람할 수 있는 사람은 누구나 메일 계정을 쓸 수 있게 된다.
1차 구현은 이 문제를 처리하지 않는다(2026-10-14 결정). 이 Tool에만 해당하는 문제가 아니며, 자격을 다루는 모든 Tool에 공통으로 필요한 플랫폼 기능이다.

**마스킹 대상 지점.**

| 지점                                        | 남을 수 있는 값                  | 비고                                                      |
| ------------------------------------------- | -------------------------------- | --------------------------------------------------------- |
| Tool 호출 기록                              | 설정 항목이 합쳐진 함수 인자     | 합치는 지점이 기록 이전이면 원문이 남음                   |
| 트레이스 (LangChain 콜백, OpenTelemetry 등) | Tool 입력 전체                   | 아래 "트레이스 주의" 참조                                 |
| Worker·자식 프로세스 로그                   | 실행 인자, 예외 메시지           | -                                                         |
| 모델에 전달되는 오류 메시지                 | 예외 메시지                      | Tool은 비밀번호를 넣지 않음. 다른 경로로 섞이는 경우 대비 |
| LLM 경유지(LiteLLM) 로그                    | 프롬프트, Tool 스키마, Tool 인자 | F-02가 끝나면 설정 항목은 여기에 오지 않음                |

**트레이스 주의.** LangChain 계열 콜백은 Tool 실행 시작 시점(`on_tool_start`)에 Tool 입력을 기록한다.
langchain-core 1.0.2부터는 `InjectedToolArg`·`ToolRuntime`으로 주입한 인자를 이 기록에서 뺀다 [1]. 플랫폼 기준 버전(1.6.5, 가이드 0장)은 여기에 해당한다.
다만 이 필터는 `on_tool_start`에만 적용되고, Tool 반환값(`on_tool_end`)이나 그래프 state 같은 다른 기록 경로에는 적용되지 않는다.
또 플랫폼이 설정값을 주입 인자가 아닌 일반 인자로 합치면 필터가 동작하지 않는다. 실제 동작은 플랫폼 구현으로 확인한다.

**방안.** 이미 자리 잡은 도구들이 쓰는 세 가지 방식을 조합한다.

| 방식           | 내용                                                                 | 사례                                                         |
| -------------- | -------------------------------------------------------------------- | ------------------------------------------------------------ |
| 필드 표시 기반 | 스키마에서 민감 항목을 표시하고, 기록 전에 그 필드 값을 치환         | JSON Schema `writeOnly` [8], Dify `secret-input` [4]         |
| 이름 기반      | 항목 이름에 `password`, `secret`, `token` 등이 들어가면 그 값을 치환 | Apache Airflow secrets masker [6]                            |
| 값 기반        | 민감 값을 등록하고, 모든 기록 출력에서 그 문자열을 치환              | GitHub Actions secret 마스킹 [5], Airflow secrets masker [6] |

필드 표시 기반을 기본으로 하고 값 기반을 함께 쓰는 것을 권장한다.
필드 표시는 구조화된 기록(호출 인자, 트레이스 속성)을 정확히 가린다. 값 기반은 예외 메시지나 서버 응답처럼 필드 밖으로 섞여 나온 값을 잡는다.
이름 기반은 표시가 빠진 항목을 위한 보조 수단이다. 이 Tool은 설정 스키마에서 `smtp_password`에 `writeOnly: true`를 표시했다(`interface.md` 3.3).
`writeOnly`는 검증 키워드가 아니라 주석이므로, 표시를 보고 실제로 가리는 일은 플랫폼이 해야 한다 [8].

**Airflow 이름 기반 동작.** Variable 이름과 Connection extra(JSON)의 키 이름을 소문자로 바꾸고 특수문자를 `_`로 바꾼 뒤,
기본 키워드(`password`, `secret`, `token`, `api_key` 등)가 부분 문자열로 들어 있으면 값을 가린다. Connection password는 이름과 무관하게 항상 가린다.
키워드는 `[core] sensitive_var_conn_names`로 추가할 수 있다. 기본 키워드 목록은 버전마다 다르다(2.10.5는 12개, 3.3.2 소스는 22개) [6].

**값 기반의 한계.** 값이 변형되면(인코딩, 분할 등) 찾지 못한다. GitHub Actions 문서도 변형된 값의 마스킹은 보장하지 않는다고 밝힌다 [5].
너무 짧은 값을 등록하면 일반 문자열까지 가려지므로, Airflow는 기본으로 5자 미만의 값은 가리지 않는다(`[logging] min_length_masked_secret`, 3.0부터) [6].

**완료 조건.**

- 테스트용 비밀번호로 Tool을 실행한 뒤, 호출 기록·트레이스·Worker 로그·LiteLLM 로그에서 그 문자열이 검색되지 않는다.
- 치환 표시(예: `***`)는 원래 값의 길이나 일부를 드러내지 않는다.
- 민감 항목이 아닌 인자(제목, 본문 등)는 그대로 기록된다.

### 3.2. F-02 Tool 설정 항목의 모델 비노출

**배경.** 설정 항목과 호출 항목을 나눴지만(`design.md` 3.3), 모델에 전달하는 Tool 스키마에 설정 항목이 들어가면 문제가 생긴다.
비밀번호가 모델 컨텍스트와 LiteLLM 로그에 남고, 모델이 설정값을 바꿔칠 수 있다.

**요구사항.**

1. 모델에 전달하는 Tool 스키마에는 호출 항목만 넣는다.
2. 플랫폼이 설정 항목을 Tool 호출 시점에 조회해 호출 항목과 합친 뒤 함수에 전달한다.
   샌드박스는 warm pool을 쓰므로(2026-10-14 결정) Pod 생성 시점에 넣지 않는다.
   Worker가 실행 단위 토큰으로 설정 조회 API에서 받아 자식 프로세스에 stdin으로만 넘긴다(`tool-설정-전달-조사.md` 3.4, 3.5).
3. 모델이 설정 항목 이름으로 인자를 넘기면 거부한다. 호출 스키마의 `additionalProperties: false`로 처리할 수 있다.
   특히 `smtp_host`를 모델이 정하면 내부망 접속과 자격 탈취가 가능하다(F-11).
   무인증 릴레이(`smtp_auth=none`)에서 모델이 `smtp_username`을 정하면 임의의 사내 주소로 위장해 보낼 수 있다.
4. 합치는 지점은 기록·트레이스 이후(자식 프로세스 실행 직전)에 두거나, F-01 마스킹을 거친다.
5. 실행 토큰은 실행 단위로 발급하고, 조회 범위를 그 실행·그 Agent에 붙은 Tool로 제한하며, 실행이 끝나면 폐기한다.

**참고 사례.** 인자를 "모델이 채우는 것"과 "설정·코드가 채우는 것"으로 나누는 방식이다.

- LangChain `InjectedToolArg`: 이 주석을 단 인자는 모델에 보내는 Tool 스키마에서 빠지고, 실행할 때 값이 주입된다 [1].
- LangChain 1.x `ToolRuntime`: Tool 함수에 `runtime` 매개변수를 두면 모델에 보이지 않고, 실행 시 런타임 값이 주입된다.
  런타임 설정값(context)의 구조는 `create_agent(context_schema=...)`로 정하고 호출할 때 `context=`로 넘긴다. LangChain 문서가 권장하는 방식이다 [2].
- Dify Tool 매개변수: Agent 앱에서 `form: llm`은 모델이 값을 추론하고, `form: form`은 Tool을 쓰기 전에 사용자가 설정한다 [3].

플랫폼은 LangChain 기반이므로(가이드 0장) `ToolRuntime`의 context로 설정을 넘기는 방식을 쓸 수 있다.
다만 context가 실행 기록·트레이스에 남을 수 있으므로, context에는 `connection_id` 같은 참조만 두고 값은 Worker가 호출 시점에 조회한다(요구사항 2).

**완료 조건.**

- 모델 요청 본문(LiteLLM 로그 기준)에 설정 항목의 이름과 값이 없다.
- 모델이 `smtp_host`를 인자로 넘긴 호출은 함수 실행 전에 거부된다.

### 3.3. F-03 설정에 저장된 민감정보 보호

**배경.** 비밀번호가 설정 저장소에 저장된다. 저장소나 설정 화면에서 원문을 볼 수 있으면 F-01·F-02와 별개로 노출된다.

**요구사항.**

- 저장할 때 암호화한다. DB 컬럼 암호화나 Secret 저장소(k8s Secret 등) 참조 중에서 플랫폼 구조에 맞게 고른다.
- 설정 조회 API와 화면은 민감 항목 원문을 돌려주지 않는다(`writeOnly`). 수정할 때만 새 값을 받는다.
- 설정 열람 권한과 수정 권한을 나눈다. 변경 이력은 남기되 값은 남기지 않는다.
- 조회 응답은 가림값으로 바꾸고, 수정 요청에 가림값이 그대로 오면 기존 값을 유지한다(Airbyte, n8n, Dify 방식, 조사 문서 2.1).
- 설정을 저장할 때와 호스트·비밀번호를 바꿀 때 연결 테스트(`check()`)를 실행한다.
- 등록한 설정은 "사용만 가능"과 "조회·수정 가능" 권한을 나눈다. 공유받은 사용자는 자격 상세를 보거나 고칠 수 없게 한다.
- 복호화한 값을 Redis 등에 캐시하지 않는다. Dify는 평문으로 24시간 캐시한다(조사 문서 2.2).

**참고 사례.** Dify는 provider 자격 중 `secret-input` 타입 필드만 테넌트 단위 키로 암호화해 저장한다.
조회할 때는 7자 이상이면 앞 2자와 뒤 2자만 남기고 가린다(소스 기준) [4].
이 문서는 원래 값의 일부도 드러내지 않는 쪽으로 완료 조건을 더 엄격하게 잡았다(F-01).

**완료 조건.** DB 직접 조회, 설정 조회 API 응답, 설정 화면 어디에서도 저장된 비밀번호 원문을 볼 수 없다.

### 3.4. F-04 실제 메일 서비스 검증

**배경.** 1차 구현의 테스트는 가짜 SMTP 서버로 한다. 실제 서비스의 동작 중 일부는 문서로만 확인했거나 확인하지 못했다.

**검증 항목.**

- Gmail: k8s 클러스터(데이터센터 IP)에서 앱 비밀번호로 처음 로그인할 때 보안 알림이나 차단이 생기는지
- Gmail: 인증 계정과 다른 `from_address`를 넣었을 때 From이 바뀌는지 (확인 완료: 계정 주소로 바뀜)
- 로그인 오류 응답 형식(`interface.md` 5.2 표)
- 실제 쓸 서비스의 계정 형식, 포트, 외부 SMTP 허용 절차, 접속 국가 제한
- 서비스별 일일 발송 한도 (Gmail 개인 계정 포함)

**완료 조건.** 실제 사용할 서비스에서 정상 발송, 로그인 실패, 수신자 거부를 각각 실행해 결과 코드를 확인한다.
그 결과로 `interface.md` 5.2와 7장을 실측값으로 고친다.

**시험 도구.** Gmail 은 `scripts/gmail_integration.py` 로 위 항목 중 데이터센터 IP 차단을 뺀 나머지를 시험할 수 있다(`interface.md` 8.3).
사내 무인증 릴레이는 `scripts/relay_integration.py` 로 시험한다(`interface.md` 8.4).

**진행 기록 (2026-10-14, 로컬 PC, Gmail 587 STARTTLS).**

| 항목                             | 결과                                                                      | 후속 조치                                                     |
| -------------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 연결 테스트 `check()`            | `ok`                                                                      | -                                                             |
| 텍스트 메일 발송                 | `sent`, `refused` 없음. 사내 메일함 도착, 한글 제목·본문 정상             | -                                                             |
| 틀린 비밀번호                    | `535 5.7.8` 응답 뒤 서버가 연결을 끊음                                    | Tool 이 `CONNECTION_FAILED`로 오분류 → `_login()` 추가로 수정 |
| 수정 후 틀린 비밀번호            | `AUTH_FAILED (SMTP 535 5.7.8)`. 없는 계정과 실제 계정 모두 같음           | -                                                             |
| HTML 메일 (표시 이름, 숨은 참조) | `sent`, 2명 접수. HTML·한글 표시 이름 정상, 숨은 참조 사본 도착 | 숨은 참조를 보낸 계정 자신으로 보내 판정 불가 → 재시험 |
| 숨은 참조 재시험 (별도 주소) | 없는 주소는 보낸 계정으로 반송(`550 5.1.1`), 받을 수 있는 주소는 정상 도착. 받는 사람 사본에 숨은 참조 없음 | - |
| 계정과 다른 발신 주소            | `sent`. Gmail 이 From 을 로그인 계정 주소로 바꿔 배달함                   | `interface.md` 7장 반영                                       |
| 없는 Gmail 수신자                | `sent`, `refused` 없음. 같은 분 안에 발신 계정으로 반송(`550 5.1.1`) 도착 | Tool 은 없는 주소를 알 수 없음                                |
| 데이터센터 IP, 일일 발송 한도 | 미실행 | k8s 샌드박스 실행 필요 |

**HTML 메일 중복 도착.** 사내 메일함에 HTML 메일이 2통 도착했다. Tool 은 수신자 2명에게 한 번씩 보냈다(`accepted_count` 2).
숨은 참조로 Gmail 계정에 간 사본이 Gmail 전달(또는 사내 계정의 메일 가져오기) 설정으로 다시 들어온 것으로 추정한다. Tool 동작과는 무관하다.

**숨은 참조가 보인 메일.** 메일 화면 하나에 "숨은 참조: (보낸 Gmail 계정)"이 표시됐다.
이번 시험은 숨은 참조를 보낸 계정 자신으로 보냈다. 보낸 계정 쪽 사본에는 Gmail 이 숨은 참조를 보여 주는 것이 정상이라, 이 화면만으로는 누출인지 가릴 수 없다.
같은 조건을 로컬 서버로 재현해 보니 Tool 이 보내는 헤더에는 `Bcc` 줄이 없고, 숨은 참조 주소는 SMTP 수신자(RCPT TO)에만 있었다.
판정을 위해 시험 스크립트 3번이 받는 사람·보낸 계정과 다른 숨은 참조 주소를 따로 묻도록 고쳤다.
재시험에서는 받는 사람 메일함으로 직접 온 사본을 열어 숨은 참조 줄이 없는지(원본 보기에 `Bcc` 줄이 없는지) 확인한다.
재시험 결과 숨은 참조 주소도 별도 배달 대상으로 처리됐다. 없는 주소는 보낸 계정으로 반송됐고, 받을 수 있는 주소에는 정상 도착했다.
받는 사람 메일함의 사본에는 숨은 참조가 보이지 않았다. 처음 화면에 보인 숨은 참조는 보낸 계정 쪽 사본의 정상 표시였다.

**없는 수신자.** Gmail SMTP 는 존재하지 않는 수신자도 제출 단계에서 접수했다(`refused` 없음).
이후 발신 계정으로 반송 메일(Mail Delivery Subsystem, `550 5.1.1 The email account that you tried to reach does not exist`)이 왔다.
반송 메일의 `X-Original-Message-ID` 는 Tool 결과의 `message_id` 와 같았다. `message_id` 로 반송을 원래 발송과 짝지을 수 있다.
따라서 Gmail 에서는 F-04 완료 조건의 "수신자 거부"가 `SEND_REJECTED` 나 `refused` 가 아니라 반송 메일로 나타난다.
`interface.md` 4.2 대로 접수는 배달을 뜻하지 않으며, Agent 는 `sent` 를 "메일 서버 접수"로만 해석해야 한다.

처음 실행에서는 로컬 conda 환경을 다른 위치에서 만들고 옮긴 탓에 CA 경로가 깨져 모든 항목이 `CONNECTION_FAILED`였다(`interface.md` 8.1).

**진행 기록 (2026-10-19, 로컬 PC, 사내 릴레이 25 STARTTLS, `smtp_auth=none`).**

Tool 을 고치기 전에 `smtplib`로 직접 1통을 보내 연동을 확인했고, 외부 Gmail 수신자에게 도착했다.
그때 RCPT 응답에 `auth=1`이 붙었다. 아래는 고친 Tool 로 `scripts/relay_integration.py`를 실행한 결과다.

| 항목 | 결과 | 후속 조치 |
| --- | --- | --- |
| 서버 기능 (EHLO) | STARTTLS, 8BITMIME, SIZE 30MB, CHARSET=EUC-KR. TLS 전후 모두 AUTH 없음 | `design.md` 2.3 반영 |
| 연결 테스트 `check()` | `ok` | - |
| 텍스트 메일 발송 | `sent`, `accepted_count` 1, `refused` 없음. Gmail 받은편지함 도착 | - |
| 한글 표시 (Gmail) | 표시 이름·제목·본문 정상. 서버의 `CHARSET=EUC-KR` 광고와 무관 | - |
| 발신 도메인 인증 (Gmail 원본 보기) | SPF none, DKIM pass(사내 도메인), DMARC pass | SPF none 원인 확인. 조치는 메일 관리자 (`design.md` 8장 17번) |
| envelope 발신자 (`Return-Path`) | 빈 값 `<>`. Tool 이 보낸 값은 릴레이 헤더 `X-MAIL-FROM`에 남음 | 반송 수신 여부 확인 필요 |
| 릴레이가 추가한 헤더 | `X-RECEIVED-IP`, `Received`에 Tool 송신 IP 기록 | 외부 노출 여부 확인 필요 (`design.md` 8장 18번) |
| `smtp_auth=login` 오설정 | `AUTH_FAILED` "지원하는 로그인 방식이 없습니다" | `interface.md` 5.2 반영 |
| k8s 샌드박스 송신 IP 허용 | 미실행 | 샌드박스 실행 필요 (`design.md` 8장 15번) |

**SPF none (원인 확인).** 사내 도메인의 공개 SPF 레코드에는 릴레이 IP가 들어 있는데도 Gmail은 SPF를 none으로 판정했다.
수신 헤더의 `Return-Path`가 `<>`(빈 발신자)였다. Tool 은 MAIL FROM 에 `smtp_username`을 보냈지만(릴레이 헤더 `X-MAIL-FROM`),
릴레이가 외부로 중계하면서 envelope 발신자를 비웠다. 빈 발신자의 SPF 는 HELO 이름(릴레이 호스트명)으로 평가하는데,
그 호스트명에는 SPF 레코드가 없어 none 이 됐다(`Received-SPF`). Tool 쪽 원인이 아니다.
DMARC는 DKIM(사내 도메인 서명, From과 정렬)으로 통과했다. 사내 도메인의 DMARC 정책이 `quarantine`이므로,
릴레이의 DKIM 서명이 빠지면 외부 수신자에게 스팸으로 분류될 수 있다.

**빈 envelope 발신자의 영향.** 빈 발신자는 원래 반송 메일(DSN) 전용이다.

- 반송: 수신 측이 배달 뒤 반송을 보내려 해도 받을 주소가 없다. `interface.md` 4.2의 "반송은 발신 주소로 도착한다"가
  사내 릴레이에서는 성립하지 않을 수 있다. 없는 주소로 보내 반송이 오는지 시험해 확인한다(확인 필요).
- 조치는 메일 관리자 쪽이다. 릴레이가 원래 envelope 발신자를 유지하게 하거나, 릴레이 호스트명에 SPF 레코드를 추가한다.

**릴레이가 추가하는 헤더.** 릴레이가 `X-RECEIVED-IP`, `Received` 헤더에 Tool 의 송신 IP를 적어 외부 수신자에게 보낸다.
k8s 에서는 클러스터 송신 IP가 노출된다. Tool 이 Message-ID·EHLO 에서 Pod 이름을 빼는 것(`design.md` 4.7)과 별개로,
릴레이 설정에서 이 헤더를 뺄지 메일 관리자와 정한다.

### 3.5. F-05 수신자 통제

**배경.** 프롬프트 인젝션을 당하면 모델이 임의 수신자에게 메일을 보낼 수 있다. 내부 자료를 본문에 담아 보내는 경우도 포함된다.
1차 구현은 총 수신자 20명 상한만 둔다.
사내 무인증 릴레이는 계정 단위 발송 한도가 없을 수 있어(확인 필요), 수신자·발송량 통제가 릴레이 정책과 이 과제에 더 의존한다.

**방안.**

1. Agent 설정 항목 `allowed_recipient_domains` 추가: 운영자가 허용 도메인을 정하고, 벗어나면 접속 전에 거부한다.
   Tool 변경만으로 가능하다. 설정 스키마가 바뀌므로 `TOOL_VERSION`을 올린다.
2. 발송 전 사용자 확인: Agent가 발송 내용을 사용자에게 보여주고 승인받은 뒤 Tool을 호출한다. 플랫폼 지원이 필요하다.
   LangChain deepagents는 `create_deep_agent(interrupt_on={...})`로 지정한 Tool을 호출하기 전에 실행을 멈추고 승인·수정·거절을 받는다.
   이 기능은 checkpointer가 있어야 동작한다 [7]. 플랫폼 기준 버전(deepagents 0.7.18)에서 같은 설정을 쓸 수 있는지는 확인 필요.

**완료 조건.** 허용 도메인 밖의 주소가 들어간 호출이 접속 전에 거부된다. 2번을 적용하면 사용자 승인 없이 발송되지 않는다.

### 3.6. F-06 OAuth2 로그인 지원

**배경.** M365는 기존 테넌트에서 2026년 12월 말부터 비밀번호 로그인(Basic 인증)이 기본 비활성화된다.
Google도 앱 비밀번호 사용을 권장하지 않는다. 1차 구현은 비밀번호 로그인만 지원한다.

**방안.** SMTP XOAUTH2(`smtplib.SMTP.auth("XOAUTH2", ...)`) 또는 HTTP API(Graph, Gmail API)를 쓴다.
호출 간 토큰을 캐시할 수 없으므로 호출마다 토큰을 새로 발급받는다. 이 때문에 토큰 엔드포인트를 네트워크 목적지로 추가 신고해야 한다.
설정 항목에 클라이언트 ID, 클라이언트 시크릿(민감 항목), 테넌트 ID 등이 추가된다. 조사 내용은 `design.md` 2.4, 2.5에 있다.

**완료 조건.** Basic 인증이 꺼진 M365 테넌트에서 발송된다.

### 3.7. F-07 첨부 파일 지원

**배경.** 1차 범위에서 뺐다.

**검토 사항.**

- 파일을 Tool에 넘기는 방법: 샌드박스 안 파일 경로, base64 인자 등. JSON 인자 크기 한도를 확인해야 한다.
- 가이드 7장의 임시 디렉터리 규칙(호출마다 생성, 호출 뒤 삭제)과 맞는지
- 서비스별 메시지 크기 한도(Gmail 25MB 등). 첨부는 base64 인코딩으로 약 33% 커진다.

### 3.8. F-08 중복 발송 방지

**배경.** Tool은 호출 간 상태를 둘 수 없으므로(가이드 10장) 같은 호출이 반복되면 중복 발송된다.
1차 구현은 `DELIVERY_UNKNOWN` 오류 코드와 Tool 설명의 재시도 금지 문안으로만 대응한다.

**방안.** 플랫폼이 Tool 호출 단위의 멱등키(예: Agent 실행 ID와 호출 ID 조합)를 기록하고, 같은 키의 재실행을 막는다.
Tool 쪽에서 처리하려면 호출 간 공유 저장소가 있어야 하므로 지금 구조에서는 불가능하다.

### 3.9. F-09 샌드박스 밖 메일 게이트웨이

**배경.** 1단계에서는 Worker가 호출 시점에 비밀번호를 받아 Tool 자식 프로세스에 넘기므로, Tool 코드가 비밀번호 원문을 본다.
Tool 코드나 의존성이 침해되거나, 같은 컨테이너의 다른 프로세스가 값을 가로채면 비밀번호가 노출된다.

**방안.** 플랫폼이 샌드박스 밖에 SMTP를 받는 메일 게이트웨이를 둔다. Tool은 게이트웨이에 실행 토큰으로 로그인하고,
게이트웨이가 토큰을 검증한 뒤 실행에 연결된 실제 계정으로 상위 메일 서버에 인증해 중계한다.
Tool 코드는 바뀌지 않고, Worker가 넘기는 설정 항목만 게이트웨이 주소와 실행 토큰으로 바뀐다.
Tool은 로그인 계정을 발신 주소로 쓰므로 계정은 실제 로그인 계정을 그대로 두고, 비밀번호 자리에만 실행 토큰을 넣는다(2026-10-15 결정).
구조와 장단점은 `tool-설정-전달-조사.md` 3.6에 있다.

**검토 사항.**

- 토큰 검증: 게이트웨이의 SMTP AUTH 단계에서 실행 토큰을 검증하는 구현 방법. 이렇게 구성한 공개 사례는 찾지 못했다.
- 상위 중계: Postfix의 발신자별 SASL 중계 같은 기존 MTA 기능을 쓸지, 직접 구현할지
- 고가용성, 그리고 등록된 모든 계정의 자격을 가진 게이트웨이 자체의 보호
- 수신자 통제(F-05)와 발송량 제한을 게이트웨이에서 함께 처리할지

**완료 조건.** 샌드박스 Pod의 env·파일·Tool 프로세스 메모리 어디에도 실제 비밀번호가 없다.
실행이 끝나 토큰을 폐기하면 게이트웨이가 그 토큰의 로그인을 거부한다.

**사내 릴레이와의 관계.** 사내 무인증 릴레이(`smtp_auth=none`)를 쓰면 샌드박스에 비밀번호가 없어 위 완료 조건이 이미 충족된다.
다만 게이트웨이는 실행 토큰으로 호출 단위를 식별하지만, 릴레이는 송신 IP로만 허용하므로 같은 IP를 쓰는 워크로드를 구분하지 못한다(`design.md` 2.3).

### 3.10. F-10 Tool 실행 격리

**배경.** 같은 컨테이너에서 같은 UID로 도는 Tool 자식 프로세스는 Worker의 `/proc/<pid>/environ`과
Worker가 읽는 파일(Secret 볼륨, ServiceAccount 토큰 등)을 읽을 수 있다(`tool-설정-전달-조사.md` 2.4).
가이드 1장의 "자식 프로세스에는 Worker의 자격을 전달하지 않는다"는 원칙은 환경 변수를 넘기지 않는 것만으로는 지켜지지 않는다.
메일 Tool에 한정되지 않는 플랫폼 공통 과제다.

**요구사항.**

1. Worker는 자기 자격을 환경 변수로 받지 않는다. 프로세스 안에서 지워도 `/proc/<pid>/environ`에는 초기값이 남는다.
2. Worker는 시작 직후 `prctl(PR_SET_DUMPABLE, 0)`로 같은 UID의 `/proc` 접근을 막는다.
3. Worker는 자식 프로세스에 설정값을 stdin으로만 넘기고, `env=`는 최소 화이트리스트로 둔다. argv 전달과 `multiprocessing`의 `fork`는 쓰지 않는다.
4. 호출이 끝나면 자식 프로세스 그룹을 종료해 백그라운드 프로세스가 남지 않게 한다.
5. Tool 실행을 Worker와 다른 UID나 다른 컨테이너로 분리하는 방안을 검토한다.
   다른 UID는 setuid 권한이 필요하고, 다른 컨테이너는 `shareProcessNamespace`를 쓰지 않아야 한다.

1~4는 Worker 구현만으로 적용할 수 있다. Worker가 읽는 파일까지 보호하려면 5가 필요하다.

**완료 조건.** Tool 프로세스에서 Worker의 environ, 자격 파일, 실행 토큰 파일을 읽으려는 시도가 실패하는 것을 테스트로 확인한다.

### 3.11. F-11 SMTP 서버 주소를 통한 내부망 접속 방지

**배경.** 2026-10-14 커밋 보안 검토에서 SSRF(서버 측 요청 위조) 가능성이 지적됐다.
`smtp_host`는 함수 안에서 형식 외에는 검사하지 않고 그대로 접속에 쓰인다. `127.0.0.1`, 사설 대역, 클러스터 내부 서비스 이름도 받는다.
`smtp_host`를 조작할 수 있는 쪽은 샌드박스 안에서 내부망의 SMTP 포트로 접속하게 만들 수 있다.
더 큰 위험은 자격 탈취다. 플랫폼이 비밀번호를 설정에서 넣어 주는데 `smtp_host`는 모델이 정할 수 있다면,
공격자 서버로 접속시켜 로그인 정보를 받아 갈 수 있다. 인증서 검증은 공격자 서버의 유효한 인증서로 통과한다.

**현재 완화.**

- 포트를 25·465·587·2525로 제한한다. 내부 API·Redis·메타데이터 서비스처럼 SMTP가 아닌 서비스에는 닿지 않는다.
- `smtp_host`는 설계상 운영자만 넣는 설정 항목이다. 모델이 설정 항목을 넘기지 못하게 하는 것은 F-02 요구사항 3이다.
- 지금 플랫폼은 입력 규격을 `input_schema` 하나만 받으므로, 비밀번호는 플랫폼이 넣고 호스트는 모델이 정하는 조합은 아직 없다.
  F-02를 구현하면서 설정 주입이 생길 때 이 조합이 가능해지므로, 그 전에 함께 처리한다.

**방안.**

| 방안 | 내용 | 담당 | 한계 |
| --- | --- | --- | --- |
| 1. 모델 입력 차단 | 설정 항목을 모델 입력에서 빼고, 모델이 넘기면 거부한다(F-02) | 플랫폼 | 운영자 오입력은 막지 못함 |
| 2. 내부 주소 거부 | IP 리터럴과 DNS 해석 결과가 사설·루프백·링크로컬이면 `CONFIG_ERROR` | Tool | 로컬 시험이 막힘. 사내 릴레이도 사설 IP로 해석되면 막힘 |
| 3. 송신 제한 | 샌드박스 NetworkPolicy egress 를 외부 465·587과 사내 릴레이 25로 좁힌다 | 플랫폼 | 현재 매니페스트는 전체 허용 |

1번은 자격 탈취 경로를 근본적으로 막으므로 필수다. 2번과 3번은 운영자 오입력과 1번 누락에 대비한 이중 방어다.
OWASP SSRF 방지 가이드도 허용 목록, 내부 주소 거부, 네트워크 계층 차단을 함께 쓰도록 권한다 [9].

**2번 구현 시 정할 것.**

- 허용 방식. 사설 대역을 일괄 거부할지, 운영자가 정한 호스트 허용 목록을 둘지 정한다(확인 필요).
  로컬 시험(`localhost:2525`, `interface.md` 8.2)과 사내 릴레이(2026-10-19 확인)를 어떻게 허용할지 함께 정한다.
- DNS 재바인딩. 호스트명을 해석해 검사한 IP로 그대로 접속해야 한다. 검사와 접속 사이에 다시 해석하면 검사를 우회할 수 있다.
  TLS 인증서는 원래 호스트명으로 검증해야 하므로, `smtplib`에서 IP 접속과 호스트명 검증을 함께 하는 방법을 찾아야 한다(확인 필요).
- 검사 범위. IPv6와 IPv4 매핑 주소(`::ffff:127.0.0.1`)까지 포함한다.

**완료 조건.**

- 모델이 `smtp_host`를 넘긴 호출이 함수 실행 전에 거부된다(F-02 완료 조건과 같다).
- 2번을 적용하면 루프백·사설·링크로컬 주소와 그 주소로 해석되는 호스트명이 접속 전에 `CONFIG_ERROR`로 거부되고, 테스트로 고정된다.
- 샌드박스에서 외부 465·587과 사내 릴레이 25 외의 SMTP 목적지로 나가는 연결이 차단된다.
